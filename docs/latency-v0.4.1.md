# LinYu iOS v0.4.1 四项延迟验证报告

## 代码与判定依据

工作分支为 `ui/android-parity`。原版参考为 Android v3.1.0（`a650066a9624681a0e3404063219435d3717fa98`），核对了登录 ViewModel、认证仓库、扫描器、设备缓存、主 ViewModel 和两种开关阀控制器。[Android v3.1.0 源码](https://github.com/yehu-imei/linyu/tree/v3.1.0)

| 路径 | 代码中可复现的等待点 | 修复 |
| --- | --- | --- |
| 登录 | 空输入会直接返回，有效提交只显示转圈。接口响应、Keychain 保存和会话发布串联。原首页刷新已经异步，但缓存账单解码仍在会话发布的同步回调内。 | `AccountView` 同一交互立即显示具体错误或「正在登录…」。`AuthManager` 单次验证并安全保存会话，`OriginalAppModel` 在新登录的首页出现后读取缓存并调度刷新。 |
| 识别水表 | 第一次在 `choose` 读取 `0x23` 找台账，绑定又读取一次。已知设备重新进 App 仍走连接，扫描列表每条广播后重排。 | `BleCentral` 扫描结束按 RSSI 排序。绑定验证使用同一连接刚取得的身份观测。台账查询合并同账户、同标准化地址的并发请求，台账 TTL 为 60 秒。已验证的 UUID 展示映射按账户保存 24 小时，扫描时可直接显示已知名称。 |
| 开阀 | BLE 已就绪时也强制断开重连，界面用一条文案覆盖连接、状态、费率和回执。云端确认依赖原版 700 ms 轮询。 | BLE 优先复用就绪连接，每次控制仍读取新 `0x23` 并核对身份，向服务端申请费率后确认连接代次，再发 `0x21`。用真实 ACK 和已保存状态进入用水页。云端保留原版轮询节奏，保存未知请求意图，第一次重试只查状态。 |
| 关阀 | BLE 在 `0x22` ACK 后仍把重连、采集、上传、写回和刷新算作「正在关闭」。云端在服务端受理后又等状态查询、结算及页面刷新。 | BLE 在关阀事实保存后显示「已确认关阀，正在结算」，保留重连、`0x85`、上传及 `0x86`。缺失 ACK 时保留重试入口，写回失败保留收据和恢复入口。云端在受理并保存待结算后退出控制页，后台读取金额，拦截仍显示旧订单的短暂状态。 |

Core Bluetooth 扫描使用 UUID。对首次遇见的未知水表，需要连接一台设备才能读自报地址并查台账。扫描阶段只解析已有的展示映射。没有有效绑定时，实际启动仍需通过 BLE 地址与服务端台账建立对应关系。展示缓存失效后会重新识别。

性能日志在操作结束时写入阶段、单调时钟耗时和结果。日志条目仅使用固定阶段名和时间数字，便于在「我的 → 设置 → 运行日志」查看 `LATENCY`。BLE 连接、服务就绪、状态帧、开阀回执、关阀回执、结算分别记录。

## 相同 Mock 条件的耗时

下列为 GitHub Actions iPhone 模拟器单次采样的累计毫秒数。BLE 固定注入 30 ms 每条命令、100 ms 重连、80 ms 台账查找、60 ms 费率请求及 150 ms 上传。登录注入 150 ms 登录响应、1,500 条本地缓存账单及独立的慢刷新。登录对照用同一内存存储替身测量会话写入，正式版 Keychain 性能待真机采集。指标「首页出现」取生产 SwiftUI 视图的 `onAppear`，是视图生命周期点。

- 登录首次出现时，基线已加载 1,500 条缓存账单，修复版尚未加载。各阶段单次绝对耗时受模拟器调度影响，尤其是注入的 HTTP 响应。
- 首次识别的 `0x23` 次数从 2 次降到 1 次。重新创建缓存对象后，UUID 展示命中用时 0 ms（毫秒取整）。本次识别后的重复点选也走展示缓存路径，实际手机点击及重启耗时待测。
- BLE 开阀对照覆盖已就绪连接。重新连接耗时仍取决于水表和 Core Bluetooth。BLE 结算总时间保留真实重连、上传及写回。
- 云端关闭之后，修复版的独立账单查询样本用时 2 ms。云端开阀测试中的轮询等待由 XCTest 夹具控制。正式版按 Android v3.1.0 的 700 ms 节奏查询确认，并单独记录每次轮询。

## 验证与交付

最终构建源提交为 `03a8b54049219d2e13a11c87fa95067e65fdbaac`。GitHub Actions 通过了 31 个 SwiftPM 核心测试、108 个 iOS 模拟器测试和 8 个 IPA 打包测试。[最终构建与制品](https://github.com/CarpediemDyn/linyu-ios/actions/runs/42025586239)

登录端到端对照基线为 `6bae142`，从旧版诊断提交 `405ff2c` 隔离，仅加入同一 Mock 会话、网络和首页挂载测试。[基线测试与阶段日志](https://github.com/CarpediemDyn/linyu-ios/actions/runs/42024891349)

测试覆盖空输入提示、登录请求去重与安全存储失败、缓存过期和账户隔离、复用连接与过期连接证明、BLE 开阀拒绝和 ACK 丢失、关阀后延迟结算及重启恢复、写回重试、云端关闭失败保留订单、关闭已受理后的旧状态及多设备消费金额隔离。无签名模拟器的系统 Keychain 写入失败由隔离存储夹具替代，正式包的会话写入继续使用系统 Keychain。

IPA 为 **LinYu-LiveContainer.ipa**，版本 **0.4.1（5）**，iPhoneOS arm64，最低 iOS 16.0。CI 完成临时签名与严格验签。下载后核对了 IPA SHA-256、Mach-O 平台、包内 7 项成员哈希及 AppIcon。

`SHA-256 214bd1e96ff898c3a7f45e14c234c527ae1090e25a54fb956c9c196f8e75b444`

真机待测项目包括短信提交后的首屏、首次遇见水表、同一水表再次点选及重进 App、信号弱时的开阀确认、真实断连后恢复结算、消费金额及写回与官方账单的对应关系。现场网络请求、校园设备台账、费率接口、云端确认及账单产生时间仍需通过实机日志确认，目前没有这几项的校园服务端实测数据。自动化使用 Mock HTTP 与 BLE，避免对真实水表发送指令。
